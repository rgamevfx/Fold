M4/M5 spatial ACES integration — 8 October 2026
Uncommitted active rewrite implementation.

The shared image graph requests the project configuration's linear Rec.709 to
ACEScg OCIO processor for spatial sources. Existing GPU color processing converts
premultiplied spatial images before composition, retaining exact alpha, source
completion/error dependencies, texture leases and configuration identity. Non-ACES
sources retain their direct RGBA16F path. No CPU image transfer or new color engine.
Motion no longer rejects spatial ACES graphs; provider capability reports the
spatial GPU build availability. No dependency versions changed.

Results:
- Spatial source GPU conversion matches CPU OCIO for opaque HDR, half-alpha HDR
  and transparent source pixels. Maximum error 2.9802322e-8, exact alpha.
- Scene working space and configuration identity match the supplied project
  profile; one explicit display conversion agrees within one byte.
- Held Rec.709 images remain unchanged after ACES evaluation.
- Source RGBA16F saturation still fails after gamut conversion, even when the
  matrix would produce finite smaller values.
- Both application mixed fixtures pass: linear Rec.709 and ACES, each 640x220
  (140800 pixels), with analytic Screen/World/Screen premultiplied composition,
  exact timing, working-space/configuration identity, no evaluation-time CPU image
  transfers, old snapshot re-evaluation and retained frames.
- Both CPU spatial contract tests pass; focused render/application Clippy pass
  with existing render warnings (two YUV dead-code, baked type complexity,
  still/renderer collapsible-if) and application source_preparation collapsible-if.
- Formatting, package boundaries and diff whitespace checks pass.

Qualification is for the pinned bundled OCIO profile on Vulkan llvmpipe. Physical
presentation, Camera Plane, agent frames, aggregate Bevy memory, picking, full M5
scene and complete M3-M5 acceptance remain open. Ordinary desktop feature still
does not enable the optional spatial GPU build automatically.
