# Further GPU and threading research

Date: 10 October 2026. Scope: GTX 1070, 8 GiB VRAM, Fold's pinned wgpu 27.0.1 and FFmpeg 6.1.1. Research and recommendations only; no runtime changes or new performance claims. Read against the root development rules, Motion rewrite plan and architecture proposal §9.3–9.4. This does not start or qualify gated M6 work.

## Main conclusion

Use additional memory to enable useful retention and bounded pipeline overlap, rather than treating allocated VRAM as a utilization target. The strongest next experiments are overlapping source preparation with outstanding GPU work, improving ProRes decoder scheduling and raw-plane transport, and fusing compatible image operations. More CPU threads recording a graph of a few compute passes is a lower-priority experiment. A dedicated asynchronous compute queue is particularly unattractive on this Pascal GPU.

The [existing audit](result.md) is the measurement source: under 230 MiB peak logical allocations in tested graphs, approximately 10.3–10.4 ms median GPU work in the full graph, and substantially longer end-to-end frame times. CPU and GPU stage intervals can overlap; subtracting medians is not a reliable attribution method. A timeline trace must establish actual gaps before predicting speedups. The profile harness intentionally waits for each requested frame, so these figures are serial-request latency, not measured steady-state pipelined application throughput. Local coordinator inspection shows admission releases after queue submission rather than imposing a global GPU completion wait; proposed overlap must address actual source preparation and request scheduling, not remove a nonexistent global wait.

## GPU memory policy

Vulkan exposes a dynamic per-heap process budget and estimated usage through `VK_EXT_memory_budget`; installed capacity is not the same as available budget. Other processes and implementation policy can change the budget. Use this as the basis for a configurable admission/retention policy with headroom and pressure eviction, rather than assuming every byte of the board's 8 GiB belongs to Fold. [Vulkan extension specification](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_memory_budget.html)

The pinned high-level wgpu adapter API exposes limits, capabilities and format features but no portable equivalent of Vulkan heap budget/usage. A real dynamic budget query therefore needs a narrowly scoped backend service; it is not a `max_buffer_size` setting. Keep Vulkan-specific querying inside existing GPU ownership infrastructure and retain a portable policy where unavailable. [wgpu 27 adapter source](https://github.com/gfx-rs/wgpu/blob/v27.0.1/wgpu/src/api/adapter.rs)

Proposed experimental points, not established optimal defaults: 1/2/4 GiB shared logical renderer limits, independently varied video retention, and 2–3 outstanding frame preparations. Count retained images, decoded planes, staging, presentation frames and externally owned native-video allocations together where possible. Driver allocations and decoder internals still require external telemetry. Increasing an unfilled limit cannot itself accelerate arithmetic or transfer bandwidth.

## Upload and allocation reuse

In wgpu 27, `Queue::write_buffer` copies into staging immediately, but GPU execution waits for the next submission; queued writes execute before its command buffers. Native writes allocate temporary staging. `write_buffer_with` can avoid an intermediate CPU copy only when the producer writes directly into its provided view; substituting `copy_from_slice` does not eliminate that copy. These details also make concurrent writers into shared uniform ranges unsafe at the application level even though the queue handle is thread-safe. [Pinned queue source](https://github.com/gfx-rs/wgpu/blob/v27.0.1/wgpu/src/api/queue.rs)

A reusable mapped staging pool or `StagingBelt` can amortize many small writes. The pinned belt has an explicit write → finish → submit → recall lifecycle. Its main benefit is cheap suballocation for many small pieces, not magically eliminating the transfer of large video planes. Test a uniform arena and completion-governed native-plane buffer reuse against the existing Fold upload pool rather than adding a second competing allocator. [Pinned staging belt source](https://github.com/gfx-rs/wgpu/blob/v27.0.1/wgpu/src/util/belt.rs)

## Pipeline concurrency before command-recording concurrency

NVIDIA recommends preparing the next frame while the GPU runs, minimizing submissions, and avoiding tiny command buffers. It also explicitly discourages overlapping graphics-queue compute with dedicated asynchronous compute on **pre-Ampere** GPUs. GTX 1070 is Pascal, so newer-GPU async-compute advice must not be applied indiscriminately. [NVIDIA Vulkan guidance, work submission](https://developer.nvidia.com/blog/vulkan-dos-donts/)

Local native-video inspection also finds fresh allocation/import on cache misses, an asynchronous CUDA copy followed by stream synchronization, and import teardown. A completion-governed reusable imported-buffer ring is a concrete candidate before adding external semaphore interop. Never simply remove the synchronization: the receiving Vulkan work needs a verified ownership and visibility handoff.

Recommended experiment: a bounded producer/consumer flow that prepares frame N+1 while frame N is submitted, retains resources until completion, and only publishes results matching current revision/request identity. Measure sustained forward throughput separately from seek-to-visible latency. A deeper queue can improve the former while worsening stale-work latency; cancellation must stop unsubmitted work and cap already submitted work. This is an application scheduling proposal, not a claim that wgpu exposes separate transfer/compute queues.

wgpu 27 native `CommandEncoder` is Send/Sync and records through mutable methods. Independent encoders can be prepared on workers and their completed command buffers submitted in dependency order; one encoder is not a concurrently mutable shared recording stream. `finish` produces a consumed submission object, so Vulkan advice to reuse recorded command buffers does not translate into resubmitting a wgpu `CommandBuffer`. [Pinned command encoder source](https://github.com/gfx-rs/wgpu/blob/v27.0.1/wgpu/src/api/command_encoder.rs), [pinned queue source](https://github.com/gfx-rs/wgpu/blob/v27.0.1/wgpu/src/api/queue.rs)

Khronos's multithreaded example concerns substantial draw workloads, requires separate per-thread pools, and warns that many small command buffers can hurt performance. Fold's short compute graph is not equivalent to that sample. First measure CPU encode cost, then consider parallel recording of coarse independent branches or expensive resource/pipeline preparation. Vulkan pool/barrier management is largely wgpu's responsibility, not something to duplicate in graph code. [Khronos command-buffer sample](https://docs.vulkan.org/samples/latest/samples/performance/command_buffer_usage/README.html)

## Decode capabilities and threading

NVIDIA's capability table supports Pascal HEVC Main/Main10, but not HEVC 4:4:4, HEVC 4:2:2 or AV1. It does not list ProRes as an NVDEC codec. Fold already qualified the user's HEVC Main10 clip on this GTX 1070; that is stronger evidence for this exact machine than a broad architecture label. Newer Blackwell 4:2:2 support does not imply support on Pascal. Published vendor throughput figures use different hardware/software/clocks and are not Fold performance forecasts. [NVIDIA NVDEC application note](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvdec-application-note/index.html)

FFmpeg 6.1.1's ProRes decoder advertises both frame and slice threading, decodes alpha, and its registered hardware configuration is VideoToolbox when enabled—not NVIDIA NVDEC. GPU ProRes on this Linux/GTX 1070 path is not a decoder flag we can enable. A custom GPU decoder would be a separate substantial codec implementation with correctness and maintenance costs. [Pinned FFmpeg ProRes decoder](https://github.com/FFmpeg/FFmpeg/blob/n6.1.1/libavcodec/proresdec2.c)

Local inspection: `crates/media/src/video.rs` already gives software decoders up to four threads, with single-thread filters/raw output and global process admission. `crates/native-video/src/helper.rs` sets one codec thread only after rejecting everything except H264/HEVC. Do not mistake that hardware helper setting for single-threaded ProRes. Benchmark ProRes 1/2/4/6/8 threads and frame versus slice mode, single clip and multiple clips, retaining alpha and exact timestamps. More threads can increase frame buffering and seek latency; a global worker budget should prevent six processes each claiming all CPUs.

NVDEC mapping waits for decode completion. NVIDIA documents separating decode and map/processing work with a producer/consumer queue, preserving decode-surface ownership until consumed. It also notes limited output surfaces and that extra threading need not help when hardware decode is saturated. Fold's existing engine-owned GPU copy releases those scarce surfaces; deleting it without a lease/lifetime design can reduce throughput. Investigate bounded ahead-of-demand decoding and copy completion, rather than treating every device-local copy as waste. The guide describes direct NVDECODE APIs; FFmpeg's wrapper internals must be inspected before assuming its methods can be moved to arbitrary threads. [NVDEC programming guide, mapping and optimized implementation](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvdec-video-decoder-api-prog-guide/index.html)

## More work on the GPU

GPU-resident intermediate processing avoids host/device traffic; asynchronous transfer overlap requires proper completion and supported hardware. NVIDIA also cautions that pinned host memory is scarce and that mapped host “zero copy” has limited usefulness on discrete GPUs. These principles support keeping color/packing on-device but do not make CUDA-specific memory/stream APIs available through portable wgpu. [CUDA best practices, data transfer](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#data-transfer-between-host-and-device)

Concrete Fold candidates, inferred from the existing audit:

- Fuse compatible adjacent pointwise color/grade/opacity/mask operations to eliminate intermediate full-frame writes and reads. A removed 1080p RGBA32F intermediate saves approximately 63.3 MiB of logical read+write traffic per frame, excluding cache effects. Preserve operation order, premultiplication, validation, HDR behavior and CPU-reference tolerance; do not fuse spatial sampling or neighborhood operations blindly.
- Move export color transform and final 16-bit/8-bit packing onto GPU, then read only the encoder's required format. That helps export, not preview that already has no image readback. Hardware encoder interop is a further, independently qualified task; ProRes alpha export still needs its actual supported software encoder contract.
- Investigate blur tiling/workgroup reuse with per-pass timing. Larger fused kernels can increase register pressure and reduce occupancy, so fewer passes alone is insufficient proof of faster execution. [CUDA best practices, register pressure and occupancy](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#register-pressure)
- Preserve GPU processing already present: native YUV conversion, image effects and display color processing. Moving small graph traversal/metadata bookkeeping to GPU would add synchronization without an established benefit.

## Evidence needed before choosing defaults

Measure cache hits/evictions, per-pass GPU time, CPU decode/read/encode intervals, submission/completion gaps, host memory, logical GPU memory and actual device usage. Compare cold/warm forward, reverse, random and repeated-loop behavior; include multi-source composition. Record GPU clocks because previous timings changed with clock state. Validate full alpha/HDR samples and cancellation/resource-pressure behavior alongside speed. Proposed budgets, threading modes, fusion and overlap remain hypotheses until those tests pass.
